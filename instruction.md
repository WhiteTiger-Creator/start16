A failed storage migration truncated the authoritative checkpoint registry at `/app/data/checkpoint_registry.json`, and the resume planner at `/app/workflow/plan_resume.go` chooses a restart point under draft rules the training governance board later reversed. The pre-migration snapshot at `/app/data/registry_snapshot_pre_migration.json` and the journal of the changes the migrator posted after it at `/app/data/registry_journal.json` survive beside the truncated file. The end state is that `/app/data/checkpoint_registry.json` holds the registry those two determine between them, in place of what is there rather than beside it, where how they combine, what an invalidation does, what a later reinstatement brings back and what order the result comes out in are decisions the training governance board settled and recorded in the run log at `/app/incident/training_governance_log.md`. The run log is where those decisions are written down for whoever does this work; it is read rather than opened by the program. A run of the planner reads `/app/data/checkpoint_registry.json` rather than rebuilding it, and what it proposes is a statement about the registry it was handed; whatever writes that registry is yours to keep or throw away -- a second Go source left beside the planner is your business, since the planner is compiled from its own file alone and nothing beside it joins that build -- because only the registry it leaves behind is read.

`/app/workflow/plan_resume.go` is a Go program, built with the toolchain installed here the way this image builds it -- cgo off, nothing fetched, the standard library and no more -- and staying a single `package main` in that one file, whose behaviour matches the board's final decisions. It does its own work: it starts no other program and hands no part of the job to an interpreter or a loaded plugin, so the answer is the work of that one file rather than of something it calls out to. That rules out `os/exec` and `plugin`, `os.StartProcess` and the `syscall` package's process entry points, and the raw `syscall.Syscall`/`RawSyscall` family too, whatever name they are imported or aliased under: those reach a new process without naming one, and a program that has no other program to start has no call for them. It carries `--input` and `--output-dir` with the defaults it already documents and declares no other option; the shard catalogue, the data incident record and the resume policy always come from their fixed absolute paths under `/app/data`, and `--input` selects the registry alone. `/app/docs/resume_contract.json` is the output contract: paths, schemas, required-field lists, container shapes, sort orders, and a note against each field saying what that field counts. What those notes leave open -- which is every rule that decides a value rather than names it -- is settled in the same run log, which is mostly routine run notes and where the later dated decision governs.

A run is correct when all of this holds of it. It finishes inside the contract's 90-second budget. `/app/output/summary.json`, `/app/output/resume_plan.json` and `/app/output/refetch_queue.jsonl` are the only files in the directory it wrote into, those same three names standing in the directory `--output-dir` gives it where the option is used, whatever that directory held to begin with, cleared contents only, with the directory itself still at the path it was given, since the run does not own it; a directory `--output-dir` names but that does not yet exist is created rather than treated as a failure. That end state is a precondition of a successful run rather than a best effort: where something in the directory cannot be cleared, the offending path is named on standard error and the run exits non-zero WITHOUT writing its artifacts, since three files standing beside content the run could not remove is not the output the contract names, and a run that returned success over such a directory would be reporting an end state it did not reach. A run that meets the contract exits nought.

These hold of the artifacts and of the program that produces them, and a run that misses any of them is not a correct one. Every value is derived from the operational inputs, the same registry yields the same three artifacts on every run, and an alternate registry yields that registry's own answer. The snapshot, the journal, the shard catalogue, the data incident record, the resume policy, the run log and `/app/docs/resume_contract.json` are the sources this work is done from rather than things it writes: nothing rewrites them and they come back byte for byte unchanged, as does the frozen `/app/workflow/.plan_resume.original.go`. The registry is the one file under `/app/data` that is replaced, and when the work is finished that directory holds exactly the files it held before -- scratch used while the registry is being rebuilt is yours, so long as none of it is still sitting there afterwards.
